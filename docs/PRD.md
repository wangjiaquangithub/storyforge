## 1. 产品概述

### 1.1 一句话定位

面向职业网文作者和小型内容工作室的、可交互可控的长篇网文智能生产工作台。

### 1.2 产品形态

- **主产品：** Web 创作工作台（浏览器访问）
- **辅助产品：** CLI 命令行工具（批量操作、脚本集成）
- **部署方式：** 本地运行（`storyforge serve`），数据存储在本地 SQLite 或 S3

### 1.3 核心流水线

```
创意(idea) → 项目概要(brief) → 大纲(outline) → 章节生成(chapter) → 质检(audit) → 修订(revise) → 导出发布(export)
```

每个阶段：
- 可独立运行
- 可串联为全自动流水线
- 支持手动/自动两种模式

## 3. 工作台详细需求

### 3.1 项目台（Project Desk）

#### 3.1.1 功能概述

项目的创建、配置、管理和全局视图。

#### 3.1.2 用户故事

**US-001：一句话创建项目**
- 作为作者，我希望能输入一句话创意就创建项目
- 这样我能快速从灵感到可执行的项目

**验收标准：**
- 输入框支持中文，占位文字示例："一个失势太子在残破灵械之城中重建王朝"
- 点击"创建项目"后，系统自动：
  - 生成项目 ID
  - 设置初始阶段为 `briefing`
  - 记录创建时间
  - 跳转到项目概览

**US-002：项目列表管理**
- 作为作者，我希望看到所有项目并按状态筛选
- 这样我能快速找到需要继续的项目

**验收标准：**
- 列表展示：项目名、题材、当前阶段、章节进度（如 `3/50`）、最后更新时间
- 支持按阶段筛选：全部、创意录入、概要生成、大纲生成、章节撰写、审查修改、发布准备
- 支持按题材筛选
- 空状态展示引导文字

**US-003：项目元信息编辑**
- 作为作者，我希望编辑项目的标题、题材、标签、目标长度
- 这样我能在创作过程中调整项目方向

**验收标准：**
- 可编辑字段：标题、题材（下拉选择）、标签（逗号分隔）、目标章节数、目标字数
- 保存后更新时间戳

**US-004：项目执行摘要**
- 作为作者，我希望看到一个仪表盘级别的项目概览
- 这样我能一眼知道项目状态

**验收标准：**
- 展示：总章节数、已完成章节数、当前阶段、总任务数、已完成任务、失败任务数、总 Token 消耗
- 展示协作者列表
- 展示质量统计（审计通过率、平均分数）

#### 3.1.3 数据结构

```
Project {
  project_id: string (UUID)
  idea: string (原始创意)
  title: string? (项目标题)
  genre: string? (题材)
  tags: string[]? (标签)
  target_chapters: number? (目标章节数)
  target_words: number? (目标字数)
  phase: enum (intake/briefing/outlining/drafting/review/publishing)
  created_at: datetime
  updated_at: datetime
  collaborators: [{ user_id, role, added_at }]
  current_chapter: number (当前章节号)
}
```

### 3.2 资产台（Asset Desk）

#### 3.2.1 功能概述

创作资产（世界观、角色卡、规则集、时间线等）的生成、编辑、版本管理。

#### 3.2.2 资产类型

| 类型 | 自动生成 | 可手动编辑 | 说明 |
|------|---------|-----------|------|
| brief（项目概要） | ✅ | ✅ | 项目整体设定文档 |
| world（世界观） | ✅ | ✅ | 世界观设定，包括地理、历史、文化、力量体系等 |
| characters（角色卡） | ✅ | ✅ | 角色设定，包括外貌、性格、动机、关系等 |
| rules（规则集） | ❌ | ✅ | 写作规则，如禁止使用某些词汇、特定句式等 |
| timeline（时间线） | ❌ | ✅ | 故事时间线，事件先后顺序 |
| outline（大纲） | ✅ | ✅ | 全书结构规划 |
| chapter（章节） | ✅ | ✅ | 具体章节内容 |
| review_note（审查意见） | ✅ | ❌ | 自动生成，不可编辑 |
| continuity_note（连续性记录） | ✅ | ❌ | 自动生成，不可编辑 |

#### 3.2.3 用户故事

**US-005：自动生成 brief**
- 作为作者，我创建项目后系统自动生成 brief
- 这样我不用从零开始写项目设定

**验收标准：**
- 创建项目后自动排队 brief 生成任务
- brief 生成后展示编辑界面，用户可修改
- brief 内容参考：创意、题材、标签、目标长度

**US-006：资产版本追溯**
- 作为作者，我希望每次编辑资产都保存为新版本
- 这样我能回滚到之前的版本

**验收标准：**
- 每次编辑点"保存为新版本"，版本号 +1
- 可查看历史版本列表
- 可对比两个版本的差异（diff 视图）
- 可回滚到指定版本（回滚本身也作为新版本记录）

**US-007：资产软删除与恢复**
- 作为作者，我希望删除不满意的资产，但能恢复
- 这样我不用怕误删重要内容

**验收标准：**
- 删除后资产进入回收站，不在主列表中显示
- 回收站展示已删除资产列表和删除时间
- 可从回收站恢复，恢复后回到原位置

**US-008：资产结构化数据**
- 作为作者，我希望角色卡等资产有结构化数据
- 这样系统能更好地利用这些数据生成章节

**验收标准：**
- 角色卡包含结构化字段：姓名、性别、年龄、性格标签、外貌描述、动机、与其他角色关系
- 世界观包含结构化字段：地理区域列表、势力列表、力量体系参数
- 结构化数据和自由文本共存

#### 3.2.4 数据结构

```
Asset {
  asset_id: string (UUID)
  project_id: string
  asset_type: enum (brief/world/characters/rules/timeline/outline/chapter/review_note/continuity_note)
  version: number
  content: string (自由文本内容)
  structured_data: object? (结构化数据)
  created_at: datetime
  updated_at: datetime
  created_by: string
  is_deleted: boolean
  deleted_at: datetime?
  lineage: { origin_asset_id: string?, parent_version_id: string? }
}
```

### 3.3 大纲台（Outline Desk）

#### 3.3.1 功能概述

全书结构设计，包括分卷、章节规划、伏笔管理。

#### 3.3.2 用户故事

**US-009：自动生成大纲**
- 作为作者，我希望基于 brief 自动生成全书大纲
- 这样我有一个起点和框架，不用从零规划

**验收标准：**
- brief 审核通过后，可触发大纲生成
- 大纲包含：卷/弧数量、每卷名称、每卷章节列表、每章简要描述
- 生成后可手动调整

**US-010：分卷/分弧结构**
- 作为作者，我希望大纲按卷/弧组织
- 这样我能看到故事的宏观结构

**验收标准：**
- 每卷有：卷号、标题、简要描述、章节列表
- 每章有：章号、标题、简要描述、关键事件
- 支持增删卷和章节

**US-011：伏笔标记与追踪**
- 作为作者，我希望在大纲中标记伏笔，并在章节生成时追踪回收
- 这样我不会忘记埋下的伏笔

**验收标准：**
- 在大纲章节中标记"此处埋下伏笔：XXX"
- 系统记录伏笔状态：未使用、已埋下、已回收
- 生成章节时，如果章节涉及伏笔回收，提示作者
- 伏笔列表视图：展示所有伏笔及其状态（后续版本）

#### 3.3.3 数据结构

```
Outline {
  asset_id: string (引用 Asset)
  arcs: [{
    arc_number: number
    arc_title: string
    arc_description: string
    chapters: [{
      chapter_number: number
      chapter_title: string
      chapter_description: string
      key_events: string[]
      foreshadowing: [{ id, description, status }]
    }]
  }]
}
```

### 3.4 生产台（Production Desk）

#### 3.4.1 功能概述

章节生成与流水线控制，核心生产环节。

#### 3.4.2 用户故事

**US-012：首轮生成**
- 作为作者，我希望一个按钮完成 brief → outline → chapter → review 四步
- 这样我能快速看到初稿

**验收标准：**
- 点击"首轮生成"后：
  1. 生成 brief（如果还没有）
  2. 生成 outline（如果还没有）
  3. 生成第 1 章
  4. 自动审查第 1 章质量
- 每步状态在任务队列中可见
- 任一步骤失败时停止并提示

**US-013：下一章生成**
- 作为作者，我希望一个按钮推进到下一章节
- 这样我能持续生产章节

**验收标准：**
- 点击"下一章"后：
  1. 参考上一章内容
  2. 参考大纲中当前章节的规划
  3. 参考世界观和角色卡
  4. 生成新章节
  5. 自动审查质量
- 章节号自动递增

**US-014：批量章节排队**
- 作为作者，我希望批量生成到目标章节
- 这样我不需要一章一章点

**验收标准：**
- 输入目标章节号（如 10）
- 系统将当前章节到目标章节之间的所有任务排队
- 队列任务自动执行
- 可随时暂停队列

**US-015：手动/自动模式切换**
- 作为作者，我希望选择自动模式（全自动推进）或手动模式（每步确认）
- 这样我能在不同场景下选择不同控制粒度

**验收标准：**
- 顶栏或项目概览中有模式开关
- **手动模式**：每生成一步都暂停，用户确认后才继续
- **自动模式**：全流程自动推进，任一步骤失败时暂停并通知
- 模式切换即时生效，不影响已在运行的任务

**US-016：任务队列管理**
- 作为作者，我希望看到所有任务的执行状态
- 这样我能知道系统正在做什么、什么失败了

**验收标准：**
- 任务列表展示：任务类型、状态（排队/运行中/完成/失败）、开始时间、完成时间
- 支持按状态筛选
- 支持重新排队失败任务
- 支持清空待处理任务

#### 3.4.3 任务状态机

```
accepted → queued → running → completed
                        → failed → waiting_retry → queued
                        → cancelled
```

#### 3.4.4 数据结构

```
TaskRecord {
  task_id: string (UUID)
  project_id: string
  task_type: enum (brief_generation/asset_bootstrap/outline_generation/chapter_generation/chapter_review/export)
  status: enum (accepted/queued/running/waiting_retry/failed/cancelled/completed)
  parent_task_id: string?
  payload: object (任务参数)
  created_at: datetime
  started_at: datetime?
  finished_at: datetime?
  error_message: string?
  retry_count: number
  progress: number (0-1)
}
```

### 3.5 质检台（QA Desk）

#### 3.5.1 功能概述

质量审计与修订，确保生成内容达标。

#### 3.5.2 审计维度（v2 目标）

| 维度 | 检查方式 | 说明 |
|------|---------|------|
| 角色连续性 | LLM 评估 | 角色性格、外貌描述是否与设定一致 |
| 物资守恒 | LLM 评估 | 物品/能力是否突然出现或消失 |
| 伏笔一致性 | LLM 评估 | 伏笔是否合理推进和回收 |
| 大纲偏离 | 规则检查 | 章节内容是否严重偏离大纲规划 |
| 节奏评估 | LLM 评估 | 章节节奏是否符合预期（快/中/慢） |
| 文风一致性 | LLM 评估 | 文风是否与项目设定一致 |
| 重复度检测 | 算法检查 | 与前面章节的段落重复率 |
| AI 痕迹检测 | LLM 评估 | 是否出现明显的 AI 生成特征 |
| 情感弧线 | LLM 评估 | 章节内情感变化是否自然 |

#### 3.5.3 用户故事

**US-017：章节自动审查**
- 作为作者，我希望每章生成后自动审查质量
- 这样我能及时发现并修复问题

**验收标准：**
- 章节生成后自动排队审查任务
- 审查结果包含：各维度评分（百分制）、问题描述、修改建议
- 审查通过（总分 ≥ 80）：章节自动标记为 approved
- 审查不通过（总分 < 80）：章节标记为 needs_revision，展示问题清单

**US-018：基于审查意见改写**
- 作为作者，我希望基于审查意见重新生成问题章节
- 这样我能用最小的代价修复问题

**验收标准：**
- 点击"基于审查改写"后：
  - 将审查意见和原章节内容一起传给 LLM
  - 生成修订版本
  - 修订版本再次接受审查
- 修订版本保存为新版本号
- 最多重试 3 次，超过后提示手动处理

**US-019：定点修复（spot-fix）**
- 作为作者，我希望只修改问题段落，不重写全章
- 这样我保留好的部分，只修复问题部分

**验收标准：**
- 用户选择要修复的具体问题
- 系统只针对问题段落生成修复内容
- 修复后替换原文，其他部分不变

#### 3.5.4 数据结构

```
AuditResult {
  audit_id: string (UUID)
  chapter_asset_id: string
  project_id: string
  overall_score: number (0-100)
  passed: boolean
  dimensions: [{
    name: string
    score: number (0-100)
    issues: [{ description, severity, suggestion }]
  }]
  created_at: datetime
  llm_usage: { provider, model, tokens_in, tokens_out }
}
```

### 3.6 发布台（Publishing Desk）

#### 3.6.1 功能概述

多格式导出与发布准备。

#### 3.6.2 导出格式

| 格式 | 说明 | 适用场景 |
|------|------|---------|
| Markdown | 标准 Markdown 格式 | 通用发布、博客、自出版 |
| 纯文本 | 无格式纯文本 | 粘贴到任意平台 |
| 起点格式 | 适配起点中文网格式要求 | 起点连载 |
| 晋江格式 | 适配晋江文学城格式要求 | 晋江连载 |

#### 3.6.3 用户故事

**US-020：多格式导出**
- 作为作者，我希望将项目导出为多种格式
- 这样我能适配不同发布平台

**验收标准：**
- 选择导出格式
- 可选导出范围：全部章节、指定章节范围（如 1-10）
- 导出文件下载或复制内容
- 导出内容包含：项目标题、卷标题、章节标题和正文

**US-021：发布前检查**
- 作为作者，我希望导出前运行质量检查
- 这样我不会把有问题的章节发布出去

**验收标准：**
- 导出前运行审计
- 展示未通过审计的章节列表
- 用户可选择忽略警告继续导出
- 导出记录：时间、格式、章节范围

#### 3.6.4 数据结构

```
ExportRecord {
  export_id: string (UUID)

  format: enum (markdown/text/qidian/jinjiang)
  chapter_range: { start: number, end: number } | "all"
  created_at: datetime
  created_by: string
  file_path: string?
  status: enum (pending/completed/failed)
}
```

## 4. 规则引擎（v2 新增）

### 4.1 三层规则架构

```
┌─────────────────────────────────────┐
│  Layer 1: 通用规则（Universal）      │
│  - 所有项目默认生效                  │
│  - 如：不出现作者名、章节长度约束     │
├─────────────────────────────────────┤
│  Layer 2: 类型规则（Genre）          │
│  - 按题材自动生效                    │
│  - 如：玄幻的力量体系约束             │
├─────────────────────────────────────┤
│  Layer 3: 自定义规则（Custom）       │
│  - 项目级自定义规则                  │
│  - 如：特定角色禁用词、禁用句式       │
└─────────────────────────────────────┘
```

### 4.2 用户故事

**US-022：配置自定义规则**
- 作为作者，我希望为我的项目配置专属写作规则
- 这样生成的内容更符合我的要求

**验收标准：**
- 项目设置中有规则编辑器
- 规则格式：文本描述，支持关键词、句式、角色行为约束
- 规则在生成章节时自动引用
- 规则违反时在审计中标注

## 6. 非功能需求

### 6.1 性能

| 指标 | 要求 |
|------|------|
| API 响应时间（非 LLM） | < 200ms (P95) |
| 前端页面加载 | < 2s |
| 任务队列处理延迟 | < 5s |
| SSE 事件推送延迟 | < 1s |

### 6.2 可用性

| 指标 | 要求 |
|------|------|
| 本地运行可用性 | 100%（不依赖外部服务，LLM 可关闭） |
| 数据持久化 | 项目数据在重启后完整保留 |
| 并发安全 | 同一项目的任务串行执行 |

### 6.3 安全

|------|------|
| API 密钥 | 通过 `.env` 文件管理，不硬编码 |
| 速率限制 | 滑动窗口限流，防止前端轮询耗尽 |
| 输入校验 | 所有用户输入经过 Pydantic 校验 |

## 9. 验收标准总则

### 9.1 v2 整体验收标准

1. 全自动模式下，流水线自动推进，失败时暂停并通知
2. 手动模式下，每步操作可控，审计结果可视化
3. 非技术用户无需命令行即可完成完整创作流程
4. 三层规则引擎可配置，支持类型规则和自定义规则
5. 多维度审计体系上线，角色连续性、伏笔、AI 痕迹可量化
6. 自动/手动模式无缝切换

### 9.2 UI 验收标准

1. 所有界面文字使用简体中文，无英文枚举值暴露
2. 暗色模式下文字对比度 ≥ 4.5:1
3. 列表项支持键盘导航
4. 错误消息在 UI 上可见，不在 console 中隐藏
5. 响应式断点下布局正确

### 9.3 API 验收标准

1. 所有端点通过 Pydantic 校验
2. 错误响应包含明确的错误码和消息
3. 速率限制正常工作
4. 任务状态正确持久化，重启后可恢复
